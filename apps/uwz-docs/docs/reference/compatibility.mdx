This page is the support contract for µWebZockets 2.1.6. It states the compiler,
platforms, dependency revisions, release form, C ABI version, and TLS policy that
the rest of the site assumes. When a support claim changes, this page changes in
the same release.

## At a glance

| Item                | Value                                                                  |
| ------------------- | ---------------------------------------------------------------------- |
| Release             | 2.1.6, released 2026-10-26                                             |
| Zig                 | 0.16.0 only                                                            |
| C ABI               | Version 1.0, frozen for the 1.x layout                                 |
| TLS                 | TLS 1.3 only                                                           |
| Supported platforms | Linux and macOS on `x86_64` and `aarch64`                              |
| Release artifact    | Git source tag; no binary archives                                     |
| Security support    | Current development revision and the latest released minor line, 2.1.x |

## Zig and toolchain

The package manifest declares `minimum_zig_version = "0.16.0"`, and the roadmap
names Zig 0.16.0 as the only supported toolchain. Treat a newer compiler as
untested even though the manifest field is a minimum. The Nix flake pins Nixpkgs
26.05 and provides the supported toolchain.

Zig fetches and compiles every native dependency. You do not need CMake, Ninja,
Go, Perl, Python, `patch`, or a system zlib installation. The first build
downloads the pinned packages into the Zig caches; later builds reuse them.

## Platform support

| Platform                               | Build target         | Runtime CI                                                        | Support claim                                        | Caveat                                                                       |
| -------------------------------------- | -------------------- | ----------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| Linux `x86_64` and `aarch64`           | Native               | Hosted runtime and sanitizer matrix                               | Supported                                            | Sanitizer builds are native Linux only                                       |
| macOS `x86_64` and `aarch64`           | Native and cross     | No hosted kqueue job; the test graph cross-compiles on demand     | Supported                                            | Cluster workers are unpinned because macOS has no hard-affinity API          |
| Windows `x86_64`                       | `x86_64-windows-gnu` | `windows-2025` runtime job plus compile and ReleaseFast libraries | Platform-gated on a green run for the release commit | No Windows binaries; ADR 0004 owns the IOCP accept and queued-close behavior |
| FreeBSD, NetBSD, OpenBSD, DragonFlyBSD | Shared build graph   | None                                                              | Community builds                                     | Compiled but not executed in CI                                              |

Linux is the platform with the complete hosted runtime and sanitizer matrix.
macOS is supported, but its kqueue coverage is recorded evidence rather than a
hosted job. Windows official support starts only when the native runtime job is
green for the release commit; until then the compile gate is the claim. The four
BSD targets share the build graph and have no dedicated runtime CI, so a BSD
deployment is a community build whose evidence belongs to the deployer.

Shared-nothing clustering is fully supported on Linux. macOS runs workers
unpinned. Windows uses the `SO_REUSEADDR` fallback and makes no worker-to-core
affinity guarantee. The framework detail is in
[Platform support](/docs/operations/platforms).

## Release policy

| Policy              | Value                                                                                |
| ------------------- | ------------------------------------------------------------------------------------ |
| Version scheme      | Semantic Versioning, recorded in `CHANGELOG.md`                                      |
| Current release     | 2.1.6, 2026-10-26                                                                    |
| Artifact            | Git source tag                                                                       |
| Binary archives     | None, for any platform                                                               |
| Fetch               | `zig fetch --save 'git+https://github.com/farbenbuilds/uWebZockets#<tag-or-commit>'` |
| Security support    | Current development revision and the latest released minor line, 2.1.x               |
| Older releases      | No backports to older tagged releases or earlier snapshots                           |
| C ABI compatibility | 1.x layout frozen; enum additions are append-only                                    |
| Unreleased tree     | May include unreleased changes; pin a tag or full commit                             |

2.1.6 is a patch release. It changes no public API, C ABI layout, capacity, wire
format, or TLS policy. The tree may contain unreleased work after a release; the
tag, not the branch, is the compatible unit.

Releases are source tags with no binary archives. Consumers fetch the tag and
let Zig build the pinned dependencies for their target. There is no Windows,
macOS, or Linux binary download to verify.

## C ABI version

| Item           | Value                                                         |
| -------------- | ------------------------------------------------------------- |
| Header         | `include/uWebZockets.h`                                       |
| ABI version    | 1.0                                                           |
| Version macros | `UWZ_VERSION_MAJOR`, `UWZ_VERSION_MINOR`, `UWZ_VERSION_PATCH` |
| Layout rule    | Field order, field types, and size are frozen for ABI 1.x     |
| Enum rule      | New values are appended; existing values are not renumbered   |
| Scope          | High-level server operations only                             |

The ABI uses opaque handles, `uwz_slice` byte views, and `uwz_error`. It fixes
1,024 connection slots, 64 routes, 32 middleware entries, 16 inline route
parameters, and a 2,048-byte route path. The low-level HTTP/2, HPACK,
HTTP/3-extension, WebTransport, UDP, and client modules remain Zig-only.

See [C ABI](/reference/c-abi) for the complete surface and
[Embed from C or C++](/docs/guides/c-abi) for the consumer build recipe.

## TLS policy

| Policy       | Value                                                                                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Protocol     | TLS 1.3 only; TLS 1.2 and older are rejected                                                                                                                    |
| ALPN         | `h2` then `http/1.1` on TCP; `h3` only on QUIC                                                                                                                  |
| Certificates | PEM chain and key, or an in-memory ephemeral certificate for development                                                                                        |
| mTLS         | `none`, `optional`, or `required`; TCP only; `required` fails the handshake closed                                                                              |
| 0-RTT        | TCP admits `GET`, `HEAD`, `OPTIONS`, and `TRACE`; other methods receive `425 Too Early`; `QUERY` is replay-unsafe; the live HTTP/3 listener disables early data |
| Rotation     | Rolling restart; no hot certificate reload                                                                                                                      |
| Cluster TLS  | One `SSL_CTX` per worker; ticket state is per worker                                                                                                            |
| Client trust | No bundled trust store; `ca_path` is required when `verify = true`; `verify = false` is development only                                                        |

A TLS-enabled cluster uses the same TLS 1.3 and ALPN policy as a single
application. Client-certificate modes disable early data because the client
certificate is checked in the second flight. The client pins TLS 1.3 as both the
minimum and maximum version and does not present a client certificate.

## Browser and protocol client compatibility

| Client            | Reaches                     | Constraint                                                                         |
| ----------------- | --------------------------- | ---------------------------------------------------------------------------------- |
| Browser, HTTP/1.1 | HTTP/1.1 over TCP or TLS    | Standard `fetch`, XHR, and navigation                                              |
| Browser, HTTP/2   | HTTP/2 over TLS via ALPN    | The browser offers `h2`; the server prefers it over `http/1.1`                     |
| Browser, HTTP/3   | HTTP/3 over QUIC            | Requires h3 support, UDP reachability, and a trusted certificate                   |
| Browser WebSocket | RFC 6455 over HTTP/1.1      | Standard WebSocket API                                                             |
| Browser RFC 8441  | WebSocket over HTTP/2       | Requires client support for extended CONNECT; one tunnel per connection            |
| curl              | HTTP/1.1, HTTP/2, or HTTP/3 | Use `--http2` or `--http3-only`; `-k` only for ephemeral certificates              |
| h2load            | HTTP/2                      | Use a current nghttp2 build; the benchmark harness requires 1.69.0 or newer        |
| wscat             | WebSocket                   | Handshake and message checks                                                       |
| `uz.client`       | HTTP/1.1 over TCP or TLS    | Numeric hosts only; no redirects, cookies, proxy, retries, mTLS, HTTP/2, or HTTP/3 |

Cleartext HTTP/2 is prior knowledge only. Browsers use TLS ALPN; the prior
knowledge path is for tools and service clients. The client compatibility row
describes the bundled outbound client, not a claim that µWebZockets ships a
browser client or an HTTP/2 client.

## What compatibility does not promise

- A runtime guarantee for Windows before its release job is green, or for any
  BSD target.
- A binary artifact for any platform.
- TLS 1.2 fallback or a configurable protocol range.
- Dynamic capacity beyond the fixed startup slab.
- An HTTP/2 or HTTP/3 client in `uz.client`.
