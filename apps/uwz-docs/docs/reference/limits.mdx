Every limit is fixed before the listener starts. This table answers three
questions for each protocol surface: what the bound is, which configuration or
compile-time value sets it, and what the caller observes when input crosses it.
The HTTP-only rejection document shape and status detail live in
[HTTP limits](/docs/http/limits); this page owns the cross-protocol matrix.

## How to read the table [#how-to-read]

- `Value` is the default for µWebZockets 2.1.6. `Fixed` means no builder
  override exists.
- `Set by` names the `ServerConfig` field, compile-time constant, or fixed ABI
  value that owns the bound.
- `On overflow` describes the caller-visible result. A closed connection has no
  application callback and no HTTP response.
- `Source` names the module that enforces the bound, not the page that explains
  it.

## Where the bounds apply [#where-the-bounds-apply]

```mermaid
flowchart LR
    accTitle: Limits diagram
    accDescr: Compare every HTTP/1.1, HTTP/2, HTTP/3, WebSocket, JSON-RPC, client, cluster, and C ABI limit with its overflow behavior.
    A[Connection admission] --> B[Protocol head]
    B --> C[Request body]
    C --> D[Router and middleware]
    D --> E[Handler]
    E --> F[Response]
```

The HTTP and WebSocket rows follow this path. A bound in an earlier layer prevents
the later layers from running, so one request usually reports the first limit it
crosses. The client, cluster, and C ABI rows are separate surfaces.

## Layered limits [#layered-limits]

Several bounds are composed from more than one value. The smaller bound wins.

| Limit                       | Composition                                                                                                     |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| HTTP/2 request body         | `min(max_body_size, max_h2_body_size)`; the first sets the runtime ceiling and the second sizes the stream slab |
| HTTP/3 request header bytes | Shared `max_header_size`; `listen_udp` rejects a value above 65,535 even though HTTP/1.1 and HTTP/2 accept it   |
| Static file body            | `write_queue_size - 4096` when the queue is larger than 4 KiB, otherwise `write_queue_size`                     |
| OpenAPI route records       | `max_route_nodes + max_pattern_routes`, which is 320 at the defaults                                            |
| Cluster inbox memory        | `64 * max_ws_message_size` plus one message-sized scratch buffer per active worker                              |
| C ABI capacity              | Fixed 1,024 connections, 64 routes, 32 middleware callbacks, 16 inline captures, and 2,048-byte paths           |

## Notes [#notes]

On HTTP/1.1, a rejection document is part of the HTTP surface, not a handler
result. The transport formats the document into fixed stack storage and writes it
through the bounded response path, so an oversized request never reaches
middleware or a route callback. The document names the limit and the byte value.
HTTP/3 returns a compact `413` body; HTTP/2 fails the stream or connection. See
[HTTP limits](/docs/http/limits) for the exact JSON shape and status codes.

The HTTP/2 body cap is enforced twice: the session rejects a declared
`content-length` above `request_body_limit`, and it resets a stream whose DATA
frames cross the per-stream slab. The HTTP/3 engine applies its body limit per
stream and returns `413` before dispatch.

Capacity changes are not hot-reloadable. Restart the process after changing a
`ServerConfig` field; the generated application type, the slab layout, and every
table on this page change together.
