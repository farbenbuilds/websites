Phần lớn framework server giúp bắt đầu throughput dễ nhưng khiến dung lượng khó
lý luận. µWebZockets bắt đầu từ hướng ngược lại: quyết định giới hạn tài
nguyên trước, rồi để hot path dùng lại chúng.

## Vấn đề của cấp phát không giới hạn

Request path thông thường cấp phát cho request, header, body, giá trị đã parse,
response part và output đang xếp hàng. Mỗi lần cấp phát thêm một chế độ lỗi:

- Allocator có thể chậm hoặc bị tranh chấp dưới tải.
- Bộ nhớ có thể tăng đến khi process bị kill.
- Độ trễ phụ thuộc allocator và garbage collector hoặc page fault.
- Quá tải đến dưới dạng timeout, reset hoặc out-of-memory thay vì lỗi có tên.

µWebZockets loại bỏ các cấp phát đó khỏi request path. `App(N)` và
`Server.builder` cấp phát một slab lúc khởi động. Buffer request, slot kết nối,
vùng message, write queue và lưu trữ router đến từ slab đó và trở lại slab khi
kết nối đóng.

## Vấn đề của trạng thái chia sẻ

Bảng kết nối hoặc queue output chia sẻ cần lock hay giao thức atomic trên mỗi
lần truy cập. Trên nhiều lõi, phối hợp đó trở thành hot path. Mô hình
shared-nothing cho mỗi worker event loop, slab và trạng thái kết nối riêng.
Giao tiếp giữa worker dùng ring lock-free có giới hạn, và một kết nối chỉ được
worker đã accept nó chạm vào.

Cái giá là trạng thái không tự động hiện diện ở mọi nơi. Nếu một message phải
đến mọi worker, dùng API publish của cluster và xử lý inbox đầy như một kết quả
có tên.

## Vấn đề của API riêng cho từng giao thức

HTTP/1.1, HTTP/2, HTTP/3 và WebSocket có framing, flow control và quy tắc vòng
đời khác nhau. Phơi một API handler riêng cho mỗi giao thức sẽ lặp lại routing,
validation và code phản hồi. µWebZockets giữ một ranh giới `Request` và
`Response`, đẩy khác biệt giao thức xuống transport:

| Lớp       | Sở hữu                                                 |
| --------- | ------------------------------------------------------ |
| Handler   | Method, target, header, body, capture của ứng dụng     |
| Router    | Khớp static, parameter và wildcard; dispatch method    |
| HTTP/1.1  | Parse có giới hạn, pipelining, keep-alive, write queue |
| HTTP/2    | Frame, HPACK, lưu trữ stream, flow control             |
| HTTP/3    | Stream QUIC, QPACK, validation request                 |
| WebSocket | Upgrade, framing, nén, pub/sub                         |

Handler vẫn thấy dữ kiện riêng của giao thức khi cần, như HTTP method hoặc
WebSocket opcode. Nó không cần cấu trúc ứng dụng thứ hai để phục vụ chúng.

## uWebZockets thay đổi gì

1. **Dung lượng là tường minh.** Kết nối, body, header, route, middleware,
   message và queue có giới hạn có tên.
2. **Sở hữu là tường minh.** Slice request được mượn cho callback;
   `Request.clone` và `req.json(T, allocator)` là các lối cấp phát được ghi.
3. **Backpressure là một giá trị.** `error.WouldBlock` bảo producer quay lại
   sau thay vì làm queue phình ra.
4. **Shutdown có tính quyết định.** Tín hiệu hoặc `request_shutdown` drain
   loop, giải phóng completion và trả về cho caller.
5. **Một API phục vụ nhiều giao thức.** Cùng một route trả lời request HTTP/1.1,
   HTTP/2 và HTTP/3; route WebSocket dùng cùng giá trị ứng dụng.

## Cái giá phải trả

Mô hình đòi hỏi nhiều hơn từ người viết ứng dụng:

- Bạn phải ước lượng dung lượng trước khi deploy.
- Giới hạn cố định không tăng theo tải; nâng dung lượng cần khởi động lại.
- Consumer chậm phải xử lý drain thay vì dựa vào buffer không giới hạn.
- Request body được buffer, nên upload lớn cần dung lượng body lớn hơn hoặc
  thiết kế khác.
- Callback chạy trên loop sở hữu; công việc blocking thuộc thread khác với
  async token.

Đây là các ràng buộc có chủ đích. [Mô hình dung lượng](https://github.com/farbenbuilds/uWebZockets/blob/main/docs/memory_model.md)
giải thích cách tính slab, và [Vì sao uWebZockets](/docs/why-uwebsockets) so
sánh đánh đổi với thiết kế khác.
