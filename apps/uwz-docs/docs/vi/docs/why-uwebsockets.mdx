µWebZockets tồn tại cho các service Zig muốn thất bại ở dung lượng đã biết
thay vì suy giảm không đoán trước dưới tải. Nó phù hợp khi bộ nhớ được lập kế
hoạch, độ trễ quan trọng và một API handler chung cho nhiều giao thức giúp
giảm code trùng lặp.

Nó không phù hợp khi bạn cần dung lượng co giãn, streaming request body, hệ
sinh thái client được quản lý, hoặc hành vi giao thức nằm ngoài bề mặt đã ghi.

## Vấn đề thiết kế giải quyết

| Vấn đề                           | Hệ quả ở server thông thường                               | Cách uWebZockets xử lý                                            |
| -------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| Cấp phát mỗi request             | Độ trễ tăng vọt, tranh chấp allocator, bộ nhớ khó đoán     | Một slab lúc khởi động; buffer request và write queue có giới hạn |
| Queue không giới hạn             | Bộ nhớ tăng đến khi process bị kill                        | Write queue cố định; producer nhận `error.WouldBlock`             |
| Trạng thái chia sẻ               | Lock và tranh chấp cache line trên hot path                | Một worker sở hữu loop, slab và trạng thái kết nối                |
| Handler riêng cho từng giao thức | Nhiều nhánh code cho HTTP/1.1, HTTP/2, HTTP/3 và WebSocket | Một ranh giới `Request` và `Response`                             |
| Giới hạn ngầm                    | Lỗi hiện ra dưới dạng timeout hoặc socket bị đóng          | Giới hạn có tên, lỗi có kiểu và rejection có cấu trúc             |

## Code thay đổi thế nào

Bạn chọn dung lượng lúc khởi động, đăng ký route trước listener đầu tiên, và
giữ công việc handler đồng bộ trừ khi dùng async token. Giá trị ứng dụng phải
ở địa chỉ ổn định khi đang listen. Công việc hoãn hoàn tất trên loop sở hữu
kết nối. Các đoạn này lược bỏ import và thân handler; [quickstart](/docs/getting-started/quickstart)
cho thấy chương trình hoàn chỉnh.

```zig
var app = try uz.App(128).init(init.io);
defer app.deinit();

_ = try app.get("/", hello);
try app.listen("0.0.0.0", 3000);
try app.run();
```

Cùng hình dạng đó mở rộng sang nhóm worker mà không đổi handler:

```zig
var group = try uz.Server.builder(init.io)
    .with_max_clients(128)
    .build_cluster(std.heap.page_allocator, 4, .{});
defer group.deinit();

const Cluster = @TypeOf(group);
try group.configure(struct {
    fn routes(worker: *Cluster.Worker, index: usize) !void {
        _ = index;
        _ = try worker.get("/", hello);
    }
}.routes);

try group.listen("0.0.0.0", 3000);
try group.run();
```

## Cái giá phải trả

Thiết kế có giới hạn là đánh đổi, không phải nâng cấp miễn phí:

- Bạn phải tính kết nối, request body, write queue, message WebSocket, route,
  middleware và trạng thái giao thức. [Mô hình dung lượng](https://github.com/farbenbuilds/uWebZockets/blob/main/docs/memory_model.md)
  ghi các giá trị mặc định.
- Cạn dung lượng là tường minh. Write queue đầy trả `error.WouldBlock`; request
  quá lớn nhận `413` hoặc `431` kèm tài liệu có cấu trúc.
- Không có tăng dung lượng động. Muốn nâng giới hạn phải đổi cấu hình và khởi
  động lại.
- Request body được buffer, không stream đến handler. Response streaming có
  qua `begin_stream`.
- Client chỉ hỗ trợ HTTP/1.1, dùng host dạng số và không có redirect, cookie,
  proxy, mTLS hay connection pooling.
- Helper WebTransport chưa nối với listener HTTP/3 live, và cluster HTTP/3
  không được hỗ trợ.
- TLS chỉ 1.3. Xoay chứng chỉ là rolling restart, không hot reload.

## Khi nào nên chọn

Chọn µWebZockets khi bạn trả lời được các câu sau trước khi deploy:

1. Số kết nối đồng thời tối đa là bao nhiêu?
2. Request body hợp lệ lớn nhất là bao nhiêu?
3. Mỗi kết nối được buffer bao nhiêu dữ liệu phản hồi?
4. Process phải phục vụ giao thức và chế độ TLS nào?
5. Bao nhiêu worker nên sở hữu slab và event loop?

Nếu các câu trả lời ổn định, mô hình dung lượng biến chúng thành một lần cấp
phát lúc khởi động và một chế độ thất bại đoán trước. Nếu chúng đổi theo từng
request, runtime khác có thể phù hợp hơn.

## Bằng chứng thay cho tuyên bố

Repository công bố workflow tuân thủ giao thức, sanitizer, fuzz và benchmark
thay vì hứa hẹn hiệu năng tuyệt đối. Benchmark là chốt chống hồi quy tương đối
trên host và commit được nêu. Đọc [roadmap và ranh giới](https://github.com/farbenbuilds/uWebZockets/blob/main/docs/roadmap.md)
trước khi lặp lại một con số trong kế hoạch production.
