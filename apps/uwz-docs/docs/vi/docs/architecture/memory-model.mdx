µWebZockets cấp phát một application slab trước khi listener đầu tiên khởi động và
tái sử dụng nó suốt vòng đời process. Trang này cho thấy `ServerConfig` biến thành
slab đó như thế nào, region nào sở hữu byte nào và runtime hành xử ra sao khi một
region đầy.

## Một slab, carve một lần

`App.init` cấp phát block qua `std.heap.page_allocator`; `App.init_configured`
và `Server.builder(...).build` dùng allocator bạn truyền vào. `App.init_from_slab`
nhận storage do caller sở hữu với cùng hợp đồng. Block được chia theo thứ tự dưới
đây, và region tùy chọn có độ dài bằng không khi feature tắt.

| #   | Region               | Byte                                                       |
| --- | -------------------- | ---------------------------------------------------------- |
| 1   | Connection pool      | `max_connections * sizeof(TcpConnection)`                  |
| 2   | Freelist index       | `max_connections * sizeof(usize)`                          |
| 3   | Request buffer       | `max_connections * request_stride`                         |
| 4   | Header extras        | `max_connections * extra_header_stride`                    |
| 5   | Route-capture extras | `max_connections * extra_route_param_stride`               |
| 6   | HTTP/2 session       | `max_connections * h2_session_stride`                      |
| 7   | Write queue          | `max_connections * write_queue_size`                       |
| 8   | WebSocket message    | `max_connections * max_ws_message_size`                    |
| 9   | RFC 7692 scratch     | `max_connections * compression_stride` khi bật compression |
| 10  | Datagram ring        | `max_connections * datagram_stride` khi bật datagram       |

AF_XDP UMEM căn theo page nằm sau các region per-connection khi chọn kernel
bypass. Storage toàn application nằm sau đó: router array được định cỡ bởi
`router_storage_bytes()`, và một metrics registry căn theo cache line khi bật
observability. `TcpConnection` là kiểu internal; kích thước của nó không thuộc
hợp đồng public. Dòng datagram chỉ hiển thị stride của payload; các mảng session
id, sequence, length và ring cũng tăng theo `max_connections * datagram_slots`.

## Stride và alignment

Cả phép tính kích thước lẫn carve dùng chung một layout planner, nên sizing và
partition không thể lệch nhau.

| Stride                     | Công thức                                                                               |
| -------------------------- | --------------------------------------------------------------------------------------- |
| `request_stride`           | `align16(max_request_line_size + max_header_size + 1024 + max_body_size)`               |
| `extra_header_stride`      | `align16((max_header_count - 64) * 2 * sizeof([]const u8))`, bằng 0 tại capacity inline |
| `extra_route_param_stride` | `align((max_route_params - 16) * 2 * sizeof([]const u8), alignOf([]const u8))`          |
| `h2_session_stride`        | `align(h2_session_bytes, Http2Session.storage_alignment)`                               |
| `compression_stride`       | `align16(2 * worst_case_scratch_bound(max_ws_message_size))`                            |

Request buffer bắt đầu trên ranh giới 16 byte. Write queue bắt đầu trên cache
line 64 byte. WebSocket message region dùng alignment 16 byte. Bản thân slab cần
`max(64, alignOf(TcpConnection))`, hoặc căn theo page khi chọn kernel bypass.
Thành phần 1024 byte trong `request_stride` là framing slack, không phải capacity
người dùng đặt.

`ServerConfig.slab_bytes()` báo footprint chính xác trước khi cấp phát. Hàm
`required_bytes` internal và `SlabLayout.carve` cùng suy ra từ một phép tính
offset. `TcpConnection` và `Http2Session` là kiểu internal, còn
`worst_case_scratch_bound` là helper internal. `slab_bytes()` không tính bảng
backend libxev, gzip pool mỗi worker, RFC 7692 engine cấp phát lazy, cluster
inbox, `SSL_CTX` mỗi worker và QUIC engine pool.

```zig
const config: uz.ServerConfig = .{
    .max_connections = 512,
    .write_queue_size = 32 * 1024,
};
const bytes = try config.slab_bytes();
std.debug.print("startup slab: {d} bytes\n", .{bytes});
```

## Preset

Mọi preset là một `ServerConfig` thường, nên field nào cũng có thể override qua
các phương thức `with_*` của builder.

| Preset                          | Connection | WS message | Write queue | Request body |
| ------------------------------- | ---------: | ---------: | ----------: | -----------: |
| `Presets.microservice`          |        256 |      8 KiB |      16 KiB |       64 KiB |
| `Presets.websocket_chat`        |        512 |     32 KiB |      32 KiB |        4 KiB |
| `Presets.file_server`           |        128 |      4 KiB |     512 KiB |        8 KiB |
| `Presets.kernel_bypass`         |        512 |      8 KiB |      32 KiB |       16 KiB |
| `Presets.webtransport_realtime` |        512 |      8 KiB |      32 KiB |        4 KiB |

HTTP/2 session nhúng trong mỗi connection chiếm phần lớn footprint. Vì vậy mỗi
preset dồn byte cho capacity mà workload của nó thực sự dùng thay vì tối đa hóa
mọi chiều.

## Cấu trúc mảng song song (SoA)

Các collection lớn được lưu thành mảng song song để một lần quét trên hot path
chỉ chạm đúng field cần thiết.

| Collection      | Layout                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| Connection pool | Slab `TcpConnection` liên tục, freelist index LIFO và activity bitmap                                    |
| Router          | Segment, child và sibling link, route bit, method handler và WebSocket behavior nằm trong các mảng riêng |
| HTTP/2 session  | State request, body và response theo từng stream, cùng HPACK storage toàn connection                     |
| Cluster inbox   | Mảng topic, payload, length và flag sau một sequence ring                                                |
| Query và form   | Bốn mảng cố định 32 entry chứa pointer và length, đều mượn từ request target                             |
| Cookie          | Bốn mảng cố định 32 entry, nạp bằng một lần quét vectorized                                              |

Acquire và release trên connection pool là O(1) và có range check. Mỗi slot nhúng
một idle timer node và chín parking slot, nên một deadline không bao giờ cấp
phát.

## Bộ nhớ inbox mỗi worker

Cluster thêm bộ nhớ nằm ngoài slab. Mỗi worker đang hoạt động giữ 64 message
`max_ws_message_size` cộng một scratch buffer cùng kích thước message. Với mặc
định 16 KiB, đó là 1.064.960 byte, khoảng 1,0 MiB mỗi worker. Chỉ worker đang hoạt
động mới cấp phát inbox, nên capacity compile lớn không giữ chỗ cho worker không
bao giờ khởi động.

## Khi cạn capacity

| Tài nguyên cạn                    | Kết quả                                                        |
| --------------------------------- | -------------------------------------------------------------- |
| Connection pool                   | Socket vừa accept bị đóng ngay; không có queue chờ slot        |
| Request line hoặc header block    | `431 Request Header Fields Too Large` kèm document có cấu trúc |
| Request body                      | `413 Payload Too Large` kèm document có cấu trúc               |
| Response write ring               | `error.WouldBlock`                                             |
| WebSocket `send`                  | `error.WouldBlock`                                             |
| Route node, pattern hoặc registry | Capacity error tại thời điểm đăng ký                           |

Input quá lớn bị từ chối, không bao giờ được mở rộng. Ring đầy áp dụng
backpressure thay vì tăng bộ nhớ; trang [Backpressure](/docs/concepts/backpressure)
cho thấy producer tiếp tục như thế nào.
