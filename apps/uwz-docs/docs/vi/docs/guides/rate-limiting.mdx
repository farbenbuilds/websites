Guide này giới hạn một route theo budget của từng tenant. Middleware không sở hữu
storage: bạn truyền bucket array, index slot và LRU link, nên toàn bộ limiter nằm
trong memory bạn allocate lúc startup.

## Bài toán

Bạn cần bound số lần một caller gọi route, từ chối phần vượt bằng status và retry
hint, và giữ quyết định allocation-free trên request path. Limiter không được
tăng kích thước khi client xoay identity.

## Giả định

- Zig 0.16.0 và µWebZockets 2.1.6 cài bằng `zig fetch --save`.
- Một worker trên `127.0.0.1:3000`. Bảng là mutable state nên không chia sẻ giữa
  các loop.
- Tenant đến từ route path, không từ header do client chọn.

## Chương trình

```zig title="src/main.zig"
const std = @import("std");
const uz = @import("uWebZockets");

fn tenant_key(req: *const uz.Request) u64 {
    const tenant = req.get_param("tenant") orelse return 0;
    return std.hash.Wyhash.hash(0, tenant);
}

fn status(_: *uz.Request, res: *uz.Response) void {
    res.text("ok") catch {};
}

pub fn main(init: std.process.Init) !void {
    var app = try uz.App(128).init(init.io);
    defer app.deinit();

    var buckets: [256]uz.middleware.RateLimitBucket = @splat(.{});
    var slots: [512]uz.middleware.RateLimitIndexSlot = @splat(.{});
    var links: [256]uz.middleware.RateLimitLink = @splat(.{});

    var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
        .rate_per_second = 5,
        .burst = 10,
        .key_fn = tenant_key,
    }, &buckets, &slots, &links);
    _ = try app.use(&limiter, uz.middleware.RateLimit.handler);

    _ = try app.get("/api/:tenant/status", status);

    try app.catch_shutdown_signals();
    try app.listen("127.0.0.1", 3000);
    try app.run();
}
```

Ba array là limiter state, không phải configuration. Không move, copy hay chia sẻ
chúng với limiter thứ hai, và giữ chúng sống tới `app.deinit()`.

## Chọn key

| Field          | Type              | Behavior                                         |
| -------------- | ----------------- | ------------------------------------------------ |
| `key_fn`       | `?RateLimitKeyFn` | Gọi trước; `u64` trả về được dùng trực tiếp      |
| `key_header`   | `?[]const u8`     | FNV-1a hash của field khi request mang field đó  |
| `key_constant` | `u64`             | Dùng khi không có function, hoặc header vắng mặt |

`key_fn` là lựa chọn an toàn nhất khi key suy ra được từ routing. `key_header` chỉ
an toàn khi trusted proxy ghi field trên mọi request. Header do client set cho
phép một client xoay key; mỗi key mới có thể evict bucket cũ, nên attacker không
refill được budget của mình nhưng có thể đẩy client khác sang bucket mới rỗng.

## Capacity và sizing

| Bound           | Value         | Rule                                 |
| --------------- | ------------- | ------------------------------------ |
| Buckets         | 256           | Số key được track cùng lúc           |
| Index slots     | 512           | `slots.len >= 2 * buckets.len`       |
| Links           | 256           | `links.len == buckets.len`           |
| Refill          | 5 token/s     | `rate_per_second`                    |
| Burst           | 10 token      | `burst`, capacity của bucket         |
| Limiter storage | Khoảng 20 KiB | 8 KiB bucket, 8 KiB slot, 4 KiB link |

Tỷ lệ slot hai-một giữ load factor của open addressing ở mức một nửa. Bảng đầy sẽ
evict head của LRU, tức bucket có refill timestamp nhỏ nhất. Refill liên tục theo
monotonic clock nên bucket idle không tích thời gian vượt burst.

## Verification

```sh
zig build run
```

```sh
for i in $(seq 1 12); do
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/acme/status
done
curl -i http://127.0.0.1:3000/api/acme/status
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/other/status
```

Loop in ra mười `200` rồi `429`. Request `-i` cho thấy `Retry-After: 1`. Request
cuối in `200` vì `other` có bucket riêng và burst vẫn đầy.

## Failure behavior

| Điều kiện                            | Kết quả                                   |
| ------------------------------------ | ----------------------------------------- |
| Hết token                            | `429 Too Many Requests` kèm `Retry-After` |
| `rate_per_second = 0` và hết token   | `429` không có `Retry-After`              |
| Bucket array rỗng                    | `429` mọi request, fail closed            |
| `slots` dưới hai lần `buckets`       | Startup `error.InvalidIndexCapacity`      |
| Độ dài `links` khác `buckets`        | Startup `error.InvalidIndexCapacity`      |
| Key trùng trong bucket array đã seed | Startup `error.DuplicateRateLimitKey`     |

Ba lỗi cuối xảy ra trước khi listener bind nên là Zig error, không phải HTTP
status.

## Accounting theo worker

Một bảng thuộc một event loop. Trong cluster, build một limiter cho mỗi worker và
nhân budget lên: client chạm `N` worker có thể tiêu burst của từng worker. Key chỉ
unique trong một bảng, và traffic redistribution reset những gì worker biết về key.

## Variations

### Một budget toàn cục

Bỏ `key_fn` và set `key_constant`. Mọi request chia sẻ một bucket, đúng cho việc
bảo vệ một endpoint đắt tiền:

```zig
var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
    .rate_per_second = 20,
    .burst = 40,
    .key_constant = 1,
}, &buckets, &slots, &links);
```

### Key theo header của trusted proxy

Khi reverse proxy ghi đè `X-Forwarded-For` trên mọi request, header mang địa chỉ
client mà proxy quan sát được:

```zig
var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
    .rate_per_second = 10,
    .burst = 20,
    .key_header = "x-forwarded-for",
}, &buckets, &slots, &links);
```

Xác nhận proxy strip `X-Forwarded-For` do client gửi trước khi thêm giá trị của
nó. Không có bảo đảm đó thì header do client kiểm soát và limiter có thể bị evict
từng key. Contract đầy đủ về option và eviction ở
[Rate limiting](/docs/http/rate-limiting).
