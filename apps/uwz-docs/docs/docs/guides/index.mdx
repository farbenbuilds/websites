Each guide is a complete recipe for one application shape. A guide gives you a
small whole program, names the capacity it assumes, shows what a rejected
request looks like, and ends with two variations you can adapt. The guides do
not re-teach the framework: when you need the full contract for a helper, the
guide links to the reference page that owns it.

## How to read a guide

| Section              | What it answers                                           |
| -------------------- | --------------------------------------------------------- |
| Problem              | The behavior you are trying to ship                       |
| Assumptions          | Toolchain, transport, worker count, and trust boundary    |
| Program              | A complete program you can copy into `src/main.zig`       |
| Verification         | Commands that prove the success and failure paths         |
| Capacity assumptions | The bounds the program relies on and where they come from |
| Failure behavior     | Status codes and errors for each rejected input           |
| Variations           | Two changes that keep the same invariants                 |

Every program is plain application code. Nothing in a guide asks you to clone,
build, or test the framework repository, and no guide uses an unbounded
allocation on the request path.

## What a guide is not

A guide is not the reference for a helper, a status code table, or a capacity
list. Those live on the page that owns the symbol. A guide also does not repeat
the canonical example program or protocol tutorial; it applies them to one
recipe and links back. When a guide and a reference page disagree, the reference
page is correct and the guide is a defect.
