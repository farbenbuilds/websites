This guide limits one route to a per-tenant budget. The middleware owns no
storage: you pass the bucket array, the index slots, and the LRU links, so the
whole limiter lives in memory you allocated at startup.

## Problem

You need to bound how often one caller can hit a route, reject the excess with a
status and a retry hint, and keep the decision allocation-free on the request
path. The limiter must not grow when a client rotates its identity.

## Assumptions

- Zig 0.16.0 and µWebZockets 2.1.6 installed with `zig fetch --save`.
- One worker on `127.0.0.1:3000`. The table is mutable state, so it is never
  shared across loops.
- The tenant comes from the route path, not from a client-chosen header.

## Program

```zig title="src/main.zig"
const std = @import("std");
const uz = @import("uWebZockets");

fn tenant_key(req: *const uz.Request) u64 {
    const tenant = req.get_param("tenant") orelse return 0;
    return std.hash.Wyhash.hash(0, tenant);
}

fn status(_: *uz.Request, res: *uz.Response) void {
    res.text("ok") catch {};
}

pub fn main(init: std.process.Init) !void {
    var app = try uz.App(128).init(init.io);
    defer app.deinit();

    var buckets: [256]uz.middleware.RateLimitBucket = @splat(.{});
    var slots: [512]uz.middleware.RateLimitIndexSlot = @splat(.{});
    var links: [256]uz.middleware.RateLimitLink = @splat(.{});

    var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
        .rate_per_second = 5,
        .burst = 10,
        .key_fn = tenant_key,
    }, &buckets, &slots, &links);
    _ = try app.use(&limiter, uz.middleware.RateLimit.handler);

    _ = try app.get("/api/:tenant/status", status);

    try app.catch_shutdown_signals();
    try app.listen("127.0.0.1", 3000);
    try app.run();
}
```

The three arrays are limiter state, not configuration. Do not move them, copy
them, or share them with a second limiter, and keep them alive until
`app.deinit()`.

## Choose the key

| Field          | Type              | Behavior                                              |
| -------------- | ----------------- | ----------------------------------------------------- |
| `key_fn`       | `?RateLimitKeyFn` | Called first; the returned `u64` is used directly     |
| `key_header`   | `?[]const u8`     | FNV-1a hash of the field when the request carries it  |
| `key_constant` | `u64`             | Used when no function is set, or the header is absent |

A `key_fn` is the safest choice when you can derive the key from routing. A
`key_header` is safe only when a trusted proxy writes the field on every request.
A header the client sets lets one client rotate keys; each new key can evict an
older bucket, so the attacker cannot refill its own budget but can push other
clients onto a fresh, empty bucket.

## Capacity and sizing

| Bound           | Value        | Rule                                    |
| --------------- | ------------ | --------------------------------------- |
| Buckets         | 256          | Simultaneously tracked keys             |
| Index slots     | 512          | `slots.len >= 2 * buckets.len`          |
| Links           | 256          | `links.len == buckets.len`              |
| Refill          | 5 tokens/s   | `rate_per_second`                       |
| Burst           | 10 tokens    | `burst`, the bucket capacity            |
| Limiter storage | About 20 KiB | 8 KiB buckets, 8 KiB slots, 4 KiB links |

The two-to-one slot ratio bounds the open-addressing load factor at one half. A
full table evicts the head of the LRU, which is the bucket with the smallest
refill timestamp. Refill is continuous and driven by the monotonic clock, so an
idle bucket does not bank time beyond the burst.

## Verification

```sh
zig build run
```

```sh
for i in $(seq 1 12); do
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/acme/status
done
curl -i http://127.0.0.1:3000/api/acme/status
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/other/status
```

The loop prints ten `200` responses and then `429`. The `-i` request shows
`Retry-After: 1`. The last request prints `200`, because `other` has its own
bucket and the burst is still full.

## Failure behavior

| Condition                                  | Result                                     |
| ------------------------------------------ | ------------------------------------------ |
| Tokens exhausted                           | `429 Too Many Requests` plus `Retry-After` |
| `rate_per_second = 0` and tokens exhausted | `429` with no `Retry-After`                |
| Bucket array empty                         | `429` on every request, failing closed     |
| `slots` below twice `buckets`              | Startup `error.InvalidIndexCapacity`       |
| `links` length differs from `buckets`      | Startup `error.InvalidIndexCapacity`       |
| Duplicate key in a pre-seeded bucket array | Startup `error.DuplicateRateLimitKey`      |

The last three fail before a listener binds, so they are Zig errors rather than
HTTP statuses.

## Per-worker accounting

One table belongs to one event loop. In a cluster, build one limiter per worker
and multiply the budget: a client that reaches `N` workers can spend the
per-worker burst on each. Keys are unique only inside one table, and traffic
redistribution resets what a worker knows about a key.

## Variations

### One global budget

Drop `key_fn` and set `key_constant`. Every request shares one bucket, which is
the right shape for protecting a single expensive endpoint:

```zig
var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
    .rate_per_second = 20,
    .burst = 40,
    .key_constant = 1,
}, &buckets, &slots, &links);
```

### Key on a trusted proxy header

When a reverse proxy overwrites `X-Forwarded-For` on every request, the header
carries the client address the proxy observed:

```zig
var limiter = try uz.middleware.rate_limit_indexed(init.io, .{
    .rate_per_second = 10,
    .burst = 20,
    .key_header = "x-forwarded-for",
}, &buckets, &slots, &links);
```

Confirm the proxy strips a client-supplied `X-Forwarded-For` before adding its
own. Without that guarantee the header is client-controlled and the limiter can
be evicted key by key. The full option and eviction contract is on
[Rate limiting](/docs/http/rate-limiting).
