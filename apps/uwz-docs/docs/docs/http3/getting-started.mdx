HTTP/3 runs the same handlers over QUIC on UDP. This tutorial serves one route on
both TCP and UDP so you can compare the protocols on the same application value,
then verifies the QUIC path with an HTTP/3 client.

## Prerequisites

- A µWebZockets project with an HTTP route. Start from
  [Your first HTTP server](/docs/examples/first-http-server).
- Zig 0.16.0.
- A `curl` build with HTTP/3 support. `curl --version` lists `HTTP3` in its
  features.

## Write the program

Replace `src/main.zig` with:

```zig title="src/main.zig"
const std = @import("std");
const uz = @import("uWebZockets");

fn index(_: *uz.Request, res: *uz.Response) void {
    res.text("Hello over HTTP/3") catch |err| {
        std.log.err("response failed: {}", .{err});
    };
}

pub fn main(init: std.process.Init) !void {
    var server = try uz.App(128).init_http3_ephemeral(init.io);
    defer server.deinit();

    _ = try server.get("/", index);

    try server.catch_shutdown_signals();
    try server.listen("0.0.0.0", 3443);
    try server.listen_udp("0.0.0.0", 8443);
    try server.run();
}
```

`init_http3_ephemeral` generates an in-memory certificate for local work. It
creates two contexts: TCP advertises `h2` and `http/1.1`, and QUIC advertises only
`h3`. The `App` value must not move after `listen_udp`.

## Run it

```sh
zig build run
```

## Verify HTTP/3

```sh
curl --http3-only -k https://127.0.0.1:8443/
```

```console
Hello over HTTP/3
```

`--http3` alone allows a fallback to HTTP/2 if the QUIC handshake fails, so it can
pass on the wrong protocol. `--http3-only` fails loudly instead.

Compare with the TCP listener:

```sh
curl --http2 -k https://127.0.0.1:3443/
```

The same handler answered both requests. Only the transport changed.

## Use production certificates

```zig
var server = try uz.App(128).init_http3(
    init.io,
    "certs/fullchain.pem",
    "certs/privkey.pem",
);
defer server.deinit();

_ = try server.get("/", index);
try server.listen("0.0.0.0", 3443);
try server.listen_udp("0.0.0.0", 8443);
try server.run();
```

`init_http3` loads the same PEM pair into the TCP and QUIC contexts. The QUIC
context still advertises `h3` only. Certificate chain order and key matching
follow the TCP TLS rules, so use the working PEM example from
[Your first TLS server](/docs/examples/first-tls-server).

## What the QUIC path uses

| Resource                  | Bound                                                         |
| ------------------------- | ------------------------------------------------------------- |
| Concurrent connections    | Configured connection capacity                                |
| Active request streams    | Engine stream pool, sized from capacity                       |
| Decoded request fields    | `max_header_count`, `max_header_size`                         |
| Request body              | `max_h3_body_size`, default 16 KiB                            |
| Response headers          | `max_h3_response_header_size`, `max_h3_response_header_count` |
| UDP payload               | 2 KiB per packet buffer                                       |
| QUIC transport parameters | PLPMTU 1200 to 1472                                           |

The engine allocates stream, header, packet, and payload slabs once in `init`.
Nothing on the datagram path allocates.

## Network requirements

- Open the UDP port in every firewall between the client and the server. HTTP/3
  fails at the first handshake when UDP is blocked, while TCP still works.
- Do not put a TCP-only load balancer in front of the QUIC listener.
- Do not enable clustering. `init_http3` and `listen_udp` are single-application
  APIs; HTTP/3 clustering is not implemented.

## Verify the boundaries

```sh
curl --http3-only -k -X CONNECT https://127.0.0.1:8443/
```

The live listener answers a plain CONNECT with `501 Not Implemented`. WebTransport
requires extended CONNECT and is not connected to the listener. See
[WebTransport status](/docs/http3/webtransport).
