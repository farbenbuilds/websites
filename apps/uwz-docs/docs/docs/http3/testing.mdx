An HTTP/3 test must prove that the request used QUIC. A client that silently
falls back to HTTP/2 passes the wrong test. Use `--http3-only` and check the
protocol line before you trust a result.

## Prerequisites

- A running application with `listen_udp`. Start from
  [HTTP/3 quickstart](/docs/http3/getting-started).
- A `curl` build with HTTP/3. `curl --version` lists `HTTP3`.
- The UDP port open on the host and on every firewall in the path.

## Prove the protocol

```sh
curl --http3-only -k -v https://127.0.0.1:8443/ 2>&1 | grep -E "ALPN|HTTP/3"
```

```console
* ALPN: server accepted h3
< HTTP/3 200
```

`--http3` alone falls back to HTTP/2 when the QUIC handshake fails, so it can
pass on the wrong transport. Keep `--http3-only` in every check.

If the handshake fails, confirm the listener is bound and the port is reachable:

```sh
ss -lunp | grep 8443
```

A bound socket with a failing client usually means the firewall drops UDP, not
that the application rejected the request.

## Compare with the TCP listener

When the app exposes both listeners, compare them:

```sh
curl --http3-only -k -s -o h3.body -w '%{http_code}\n' https://127.0.0.1:8443/items
curl --http2 -k -s -o h2.body -w '%{http_code}\n' https://127.0.0.1:3443/items
cmp h2.body h3.body
```

Both statuses and both bodies must match. The same router and handler answered
both requests; a difference points to a transport-specific response path.

## Body limit

```sh
head -c 20000 /dev/zero | tr '\0' 'a' > large.bin
curl --http3-only -k -i --data-binary @large.bin https://127.0.0.1:8443/echo
```

With the default `max_h3_body_size` of 16 KiB, expect `413 Payload Too Large`.
Raise the capacity in your builder, rebuild, and repeat. Then send a second
request on a new connection and confirm it still succeeds; a body rejection is
stream-scoped.

## Content-type rule

```sh
curl --http3-only -k -X QUERY --data '{"filter":"active"}' \
  https://127.0.0.1:8443/search
```

Expect `400 Bad Request` before your handler runs. Add a valid `Content-Type` and
expect your handler's response. See
[QUERY over HTTP/3](/docs/http3/query-method).

## Route tests

Test request parsing and response shaping as pure functions in your project:

```zig
const std = @import("std");

fn acceptsJson(content_type: []const u8) bool {
    return std.mem.startsWith(u8, content_type, "application/json");
}

test "query media type" {
    try std.testing.expect(acceptsJson("application/json; charset=utf-8"));
    try std.testing.expect(!acceptsJson("text/plain"));
}
```

```sh
zig test src/http/media.zig
```

The transport enforces content-type syntax; this test covers your media-type
policy.

## Load and capacity

HTTP/3 load generators are less common than HTTP/1.1 tools. Use an HTTP/3-capable
client or a small service test that opens many connections, and report:

- Handshakes completed and handshakes failed.
- Requests per second and latency percentiles.
- Stream resets by code.
- Process RSS against the expected engine and slab memory.

Run the client on a separate host. A loopback run measures the client.

## Upstream evidence

The framework maintainers run an interoperability gate before a release with
pinned curl/ngtcp2 and aioquic clients. It covers the normal request path, a valid
trailing field section, duplicate pseudo-headers, pseudo-header ordering,
connection-specific headers, a healthy sibling stream on the same connection, a
header-pool soak, and a clean shutdown.

That gate describes the framework build, not your application. It is the reason a
protocol-level claim can be made; it is not a command you run in your project.
