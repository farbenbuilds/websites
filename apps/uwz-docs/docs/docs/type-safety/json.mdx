JSON crosses two typed boundaries: a request body becomes a Zig value, and a Zig
value becomes response bytes. The allocator and the output buffer are always
explicit, so the handler can state its memory bound at the call site.

## Decode a request body

```zig
const std = @import("std");
const uz = @import("uWebZockets");

const Note = struct {
    text: []const u8,
};

fn create(req: *uz.Request, res: *uz.Response) void {
    const parsed = req.json(Note, std.heap.page_allocator) catch |err| {
        std.log.warn("json parse failed: {}", .{err});
        res.end_best_effort("400 Bad Request", "invalid json");
        return;
    };
    defer parsed.deinit();

    var buffer: [256]u8 = undefined;
    res.json_buf(.{ .ok = true, .text = parsed.value.text }, &buffer) catch |err| {
        std.log.err("json response failed: {}", .{err});
    };
}
```

`req.json(T, allocator)` returns `std.json.Parsed(T)`. The allocator owns the
decoded value, including nested strings and arrays. Call `deinit` exactly once;
do not free individual fields.

`Request.json` does not inspect `Content-Type`. It parses the body bytes whatever
the media type. Check the media type first when the route accepts more than JSON.

## Response methods

| Method                              | Storage                                         | Failure                                                                          |
| ----------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------- |
| `res.json(value, allocator)`        | Temporary allocator render, freed before return | `OutOfMemory` from render; `WouldBlock` or `ResponseAlreadyStarted` from send    |
| `res.json_buf(value, buffer)`       | Caller buffer                                   | `BufferOverflow` from render; `WouldBlock` or `ResponseAlreadyStarted` from send |
| `res.json_value(value, allocator)`  | Same as `json` for `std.json.Value`             | Same as `json`                                                                   |
| `res.json_value_buf(value, buffer)` | Same as `json_buf` for `std.json.Value`         | Same as `json_buf`                                                               |
| `res.begin_json()`                  | Fixed stack coalescing buffer                   | `ResponseAlreadyStarted`; stream writes report `WriteFailed`                     |

All four fixed methods send `200 OK` with
`Content-Type: application/json; charset=utf-8`. `json` and `json_buf` accept any
type `std.json.Stringify` supports. The `json_value` variants take a dynamic
`std.json.Value`.

`json` allocates only the temporary rendering. It frees that buffer before the
helper returns, and the response queue owns its own copy of the bytes. The
allocator you pass is otherwise untouched.

A fixed body is rendered and queued in one step. On HTTP/1.1, if the rendered
body does not fit the write queue, `json` returns `error.WouldBlock`. Use
`begin_json` when the document can exceed the queue.

## Validate while decoding

`req.validate_json(T, allocator)` parses the body and applies the rules in
`T.validation`. `req.validate_json_detailed(T, allocator, &issue)` reports the
first rejected field and constraint.

```zig
var issue = uz.schema.Issue{};

const parsed = req.validate_json_detailed(CreateUser, std.heap.page_allocator, &issue) catch |err| {
    if (err == error.ConstraintViolation or err == error.MalformedJson) {
        res.end_best_effort("422 Unprocessable Entity", @tagName(issue.kind));
        return;
    }
    res.end_best_effort("500 Internal Server Error", "validation failed");
    return;
};
defer parsed.deinit();
```

`ConstraintViolation` means a declared rule rejected the value.
`MalformedJson` means parsing failed before a rule ran. An allocation failure is
`error.OutOfMemory`. See
[Schema validation](/docs/type-safety/schema-validation) for the rule fields and
issue kinds.

## Stream a large response

`begin_json()` streams a chunked JSON response through a fixed stack buffer. See
[JSON responses](/docs/http/json#streaming-responses) for the stream methods and
backpressure behavior.

## Size limits

Request bodies are bounded by `ServerConfig.max_body_size`; `json_buf` is bounded
by the caller buffer; fixed responses are bounded by the HTTP/1.1 write queue.
See [JSON responses](/docs/http/json#size-limits) for the full table and failure
mapping.

## Ownership rules

| Value                        | Owner                              | Lifetime                         |
| ---------------------------- | ---------------------------------- | -------------------------------- |
| `Parsed(T)`                  | The allocator passed to `req.json` | Until `deinit`                   |
| `req.text()` / `req.bytes()` | The connection request             | The handler callback             |
| `json_buf` buffer            | The caller                         | The call; the queue copies bytes |
| `res.json` temporary render  | The allocator                      | Freed before the call returns    |
| `JsonStream`                 | The caller                         | Until `end`; keep it stable      |

Do not store a request slice after the handler returns. Copy it with the same
explicit allocator when it must outlive the request.
