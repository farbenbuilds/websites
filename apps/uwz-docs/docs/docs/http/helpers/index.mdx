Helpers are the small composable utilities in `uz` that do not own a protocol.
They parse what a request carries, keep bounded state around a response,
transform bytes you already produced, or adapt another transport to a
pull-based stream.

At request time, every helper borrows from a bounded buffer, writes into caller
storage, or returns a compile-time fixed view. The HTTP gzip pool allocates at
application init. A `CompressionStream` or `DecompressionStream` allocates its
codec in `init`, so treat that init as an explicit allocation, not a hidden
request-path cost.

  <Card title="Query and form parsing" href="/docs/http/helpers/query-and-forms" icon="search">

  <Card title="Multipart parsing" href="/docs/http/helpers/multipart" icon="paperclip">

## State

<CardGroup cols={2}>
  <Card title="Cookies and signed cookies" href="/docs/http/helpers/cookies" icon="cookie">
    `uz.cookie` reads RFC 6265 pairs, formats `Set-Cookie` attributes, and verifies HMAC-SHA256
    signatures with rotating keys.
  </Card>
  <Card title="Caching and ETags" href="/docs/http/helpers/caching" icon="tag">
    `uz.cache` generates a strong ETag from a body and answers a conditional GET with `304 Not
    Modified`.
  </Card>
</CardGroup>

## Boundaries

A helper never decides how bytes reach the wire. HTTP/1.1 parsing, response
framing, chunked transfer, and keep-alive belong to
[HTTP/1.1 and the application API](/docs/http). WebSocket handshake, framing,
masking, and compression stay in the protocol documentation at
`docs/websocket.md`.

The following are deliberately outside this group:

- CORS, authentication, rate limiting, and security headers. They are security
  controls documented under [middleware](/docs/http/middleware).
- JSON, streaming, SSE, chunked output, static files, and OpenAPI. They are core
  response modes in the HTTP section.
- `uz.schema` and typed RPC. They are type-safety features, not utilities.
