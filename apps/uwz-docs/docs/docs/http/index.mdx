This section covers how µWebZockets parses an HTTP/1.1 request, matches a route,
runs your handler, and writes the response. It also maps the application API
that HTTP/1.1, HTTP/2, and HTTP/3 share, so the route and handler pages stay
useful when you add another transport.

Read [Server lifecycle](/docs/http/server-lifecycle) first when you are writing
startup code. Read [Handlers](/docs/http/handlers) first when the application
already starts and you need the callback contract.

## One application surface

One `uz.App(N)` value owns the route table and the connection pool. Each request
gets a borrowed `Request` and a `Response` writer. Routes, `Request`, `Response`,
and the async token do not change when the transport changes. HTTP/1.1 adds the
wire rules that the protocol pages own:

| Listener     | Transport                 | Framing and flow control                                   |
| ------------ | ------------------------- | ---------------------------------------------------------- |
| `listen`     | TCP, plaintext or TLS 1.3 | Content-Length or chunked, one write ring per connection   |
| `listen_udp` | QUIC                      | HTTP/3 stream framing, response bounded by the write queue |

The TCP TLS context advertises ALPN `h2` then `http/1.1`, so a browser can
negotiate HTTP/2 on the same listener. Request handling still enters the same
router.

## The HTTP/1.1 contract

The TCP connection accumulates one bounded request until the parser can prove
it is complete. Pipelined bytes stay in the buffer and are parsed again after
the response completes.

| Topic                                                 | Behavior                                                                                                                                                            |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request target                                        | Origin-form, absolute-form for `http` and `https`, and `*` for server-wide `OPTIONS`. Authority-form, fragments, and userinfo are rejected.                         |
| Malformed input                                       | `400 Bad Request`, then the connection closes                                                                                                                       |
| `Expect: 100-continue`                                | Answered automatically before the body is read; any other `Expect` value returns `417 Expectation Failed`                                                           |
| Oversized body                                        | `413 Payload Too Large` with a JSON document naming the limit and value                                                                                             |
| Oversized request line, header block, or header count | `431 Request Header Fields Too Large` with the same document shape                                                                                                  |
| Response framing                                      | The library generates `Content-Length` or chunked framing. A caller-supplied `Content-Length` or `Transfer-Encoding` field is rejected with `error.InvalidHeaders`. |
| Keep-alive                                            | Bounded by `idle_timeout_ms`, 120 seconds by default. `Connection: close` is honored.                                                                               |

Large fixed bodies must fit the per-connection write queue. A body that cannot
fit returns `error.WouldBlock` from `Response.end`; use a streaming body for
larger payloads. The [HTTP limits](/docs/http/limits) page lists every bound.

## Names and boundaries

Route registration uses one name per method: `get`, `post`, `put`, `delete`,
`patch`, `options`, `head`, `trace`, `query`, and `any`. The context and async
variants keep the same names: `route_context`, `route_async`,
`route_async_context`, and the GET shortcuts `get_context`, `get_async`, and
`get_async_context`.

Every failure in this section names both the HTTP status and the Zig error when
one exists. Startup calls have no HTTP status because no request exists yet;
they return a named error instead.

## Verify

The [quickstart](/docs/getting-started/quickstart) program is the smallest
server that proves this section's baseline:

```sh
curl -i http://127.0.0.1:3000/
```

The response starts with `HTTP/1.1 200 OK`, and the body is the text the handler
passed to `res.text`.
