The architecture section explains how one application value becomes bounded
runtime behavior. Read it when a preset, a latency number, or a shutdown failure
needs an explanation below the signal that you observe.

## Public contract and internals

Two layers share this section. The public layer is what your application may
name and depend on. The internal layer explains how that contract is delivered
and may change between releases.

| Layer    | Includes                                                                                            | Stability                            |
| -------- | --------------------------------------------------------------------------------------------------- | ------------------------------------ |
| Public   | `App`, `Server`, `ServerConfig`, `Presets`, `Request`, `Response`, `AsyncResponse`, cluster types   | Documented names, limits, and errors |
| Internal | libxev loop wrapper, slab planner, completion callbacks, router arrays, worker group, cluster inbox | Implementation detail                |

Public means documented on this site as a consumer entry point. Some modules are
exported so framework internals and direct integrations can reach them, but they
are not a stable consumer contract; the page labels those internal. Treat an
undocumented symbol as internal even when the compiler can name it. A page never
presents an internal entry point as public API, and no page asks you to read
framework source to use the library.

## How to read this section

Start with [Shared-nothing workers](/docs/architecture/shared-nothing) and
[Slab and memory model](/docs/architecture/memory-model) to learn what one
worker owns and how that ownership is sized. Then read
[Event loop and completions](/docs/architecture/event-loop) and
[Callback lifecycle](/docs/architecture/callback-lifecycle) to follow work
through the loop. Read [Shutdown ordering](/docs/architecture/shutdown) when a
drain or a release fails.

If you are choosing capacities, go directly to the memory model and then to the
[Capacity model](/docs/concepts/capacity-model). If you are debugging a request,
start from the [Request lifecycle](/docs/concepts/request-lifecycle).
