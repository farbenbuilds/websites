µWebZockets allocates one application slab before the first listener starts and
reuses it for the process lifetime. This page shows how `ServerConfig` becomes
that slab, which region owns each byte, and how the runtime behaves when a
region is full.

## One slab, carved once

`App.init` allocates the block through `std.heap.page_allocator`;
`App.init_configured` and `Server.builder(...).build` use the allocator you pass.
`App.init_from_slab` accepts caller-owned storage with the same contract. The
block is partitioned in the order below, and an optional region has zero length
when its feature is off.

| #   | Region               | Bytes                                                         |
| --- | -------------------- | ------------------------------------------------------------- |
| 1   | Connection pool      | `max_connections * sizeof(TcpConnection)`                     |
| 2   | Freelist indices     | `max_connections * sizeof(usize)`                             |
| 3   | Request buffers      | `max_connections * request_stride`                            |
| 4   | Header extras        | `max_connections * extra_header_stride`                       |
| 5   | Route-capture extras | `max_connections * extra_route_param_stride`                  |
| 6   | HTTP/2 sessions      | `max_connections * h2_session_stride`                         |
| 7   | Write queues         | `max_connections * write_queue_size`                          |
| 8   | WebSocket messages   | `max_connections * max_ws_message_size`                       |
| 9   | RFC 7692 scratch     | `max_connections * compression_stride` when compression is on |
| 10  | Datagram rings       | `max_connections * datagram_stride` when datagrams are on     |

Page-aligned AF_XDP UMEM follows the per-connection regions when kernel bypass
is selected. Application-wide storage follows it: router arrays sized by
`router_storage_bytes()`, and one cache-line-aligned metrics registry when
observability is on. `TcpConnection` is an internal type; its size is not part of
the public contract. The datagram row shows the payload stride only; the session
id, sequence, length, and ring arrays also scale with
`max_connections * datagram_slots`.

## Strides and alignment

Both the size computation and the carve use one layout planner, so sizing and
partitioning cannot disagree.

| Stride                     | Formula                                                                                  |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| `request_stride`           | `align16(max_request_line_size + max_header_size + 1024 + max_body_size)`                |
| `extra_header_stride`      | `align16((max_header_count - 64) * 2 * sizeof([]const u8))`, zero at the inline capacity |
| `extra_route_param_stride` | `align((max_route_params - 16) * 2 * sizeof([]const u8), alignOf([]const u8))`           |
| `h2_session_stride`        | `align(h2_session_bytes, Http2Session.storage_alignment)`                                |
| `compression_stride`       | `align16(2 * worst_case_scratch_bound(max_ws_message_size))`                             |

Request buffers start on a 16-byte boundary. Write queues start on a 64-byte
cache line. WebSocket message regions use 16-byte alignment. The slab itself
requires `max(64, alignOf(TcpConnection))`, or page alignment when kernel bypass
is selected. The 1024-byte term in `request_stride` is framing slack, not a user
capacity.

`ServerConfig.slab_bytes()` reports the exact footprint before allocation. The
internal `required_bytes` function and `SlabLayout.carve` derive from the same
offset computation. `TcpConnection` and `Http2Session` are internal types, and
`worst_case_scratch_bound` is an internal helper. `slab_bytes()` excludes the
libxev backend table, per-worker gzip pools, RFC 7692 engines allocated lazily,
cluster inboxes, per-worker `SSL_CTX` objects, and QUIC engine pools.

```zig
const config: uz.ServerConfig = .{
    .max_connections = 512,
    .write_queue_size = 32 * 1024,
};
const bytes = try config.slab_bytes();
std.debug.print("startup slab: {d} bytes\n", .{bytes});
```

## Presets

Every preset is a plain `ServerConfig`, so any field remains overridable through
the builder's `with_*` methods.

| Preset                          | Connections | WS message | Write queue | Request body |
| ------------------------------- | ----------: | ---------: | ----------: | -----------: |
| `Presets.microservice`          |         256 |      8 KiB |      16 KiB |       64 KiB |
| `Presets.websocket_chat`        |         512 |     32 KiB |      32 KiB |        4 KiB |
| `Presets.file_server`           |         128 |      4 KiB |     512 KiB |        8 KiB |
| `Presets.kernel_bypass`         |         512 |      8 KiB |      32 KiB |       16 KiB |
| `Presets.webtransport_realtime` |         512 |      8 KiB |      32 KiB |        4 KiB |

The embedded HTTP/2 session dominates the per-connection footprint. Each preset
therefore spends bytes on the capacity its workload exercises instead of
maximizing every dimension.

## Structure of arrays

Large collections are stored as parallel arrays so a hot scan touches only the
fields it needs.

| Collection      | Layout                                                                                                          |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| Connection pool | Contiguous `TcpConnection` slab, LIFO freelist indices, and an activity bitmap                                  |
| Router          | Node segments, child and sibling links, route bits, method handlers, and WebSocket behaviors as separate arrays |
| HTTP/2 session  | Per-stream request, body, and response state, plus connection-wide HPACK storage                                |
| Cluster inbox   | Topic, payload, length, and flag arrays behind a sequence ring                                                  |
| Query and form  | Four fixed 32-entry arrays of pointers and lengths, all borrowed from the request target                        |
| Cookies         | Four fixed 32-entry arrays populated by a vectorized scan                                                       |

Acquire and release on the connection pool are O(1) and range-checked. Each slot
embeds one idle timer node and nine parking slots, so a deadline never allocates.

## Per-worker inbox memory

A cluster adds memory outside the slab. Each active worker reserves 64 messages
of `max_ws_message_size` plus one message-sized scratch buffer. At the 16 KiB
default that is 1,064,960 bytes, about 1.0 MiB per worker. Only active workers
allocate an inbox, so a large compiled capacity does not reserve memory for
workers that never start.

## What exhaustion looks like

| Resource exhausted                 | Result                                                               |
| ---------------------------------- | -------------------------------------------------------------------- |
| Connection pool                    | The accepted socket is closed immediately; no queue waits for a slot |
| Request line or header block       | `431 Request Header Fields Too Large` with a structured document     |
| Request body                       | `413 Payload Too Large` with a structured document                   |
| Response write ring                | `error.WouldBlock`                                                   |
| WebSocket `send`                   | `error.WouldBlock`                                                   |
| Route nodes, patterns, or registry | A capacity error at registration                                     |

Oversized input is rejected, never expanded. A full ring applies backpressure
instead of growing memory; the [Backpressure](/docs/concepts/backpressure) page
shows how a producer resumes.
