`init_https_ephemeral` generates an ECDSA P-256 key and a self-signed X.509
certificate with BoringSSL at startup. There is no `openssl` command, no `.pem`
file, and no shared configuration to keep in sync with a teammate. The same call
is available over the C ABI.

## Start a local HTTPS server

```zig src/main.zig
const std = @import("std");
const uz = @import("uWebZockets");

fn index(_: *uz.Request, response: *uz.Response) void {
    response.text("hello from ephemeral TLS") catch |err| {
        std.log.err("response failed: {}", .{err});
    };
}

pub fn main(init: std.process.Init) !void {
    var server = try uz.App(128).init_https_ephemeral(init.io);
    defer server.deinit();

    _ = try server.get("/", index);
    try server.catch_shutdown_signals();
    try server.listen("0.0.0.0", 3443);
    try server.run();
}
```

```sh
zig build run
curl -k https://127.0.0.1:3443/
```

The response body is `hello from ephemeral TLS`. `-k` disables certificate
verification because the generated certificate is self-signed and no client
trusts it automatically.

## What the generated certificate contains

| Field             | Value                                                      |
| ----------------- | ---------------------------------------------------------- |
| Key               | ECDSA P-256, signed with SHA-256                           |
| Subject           | `CN=localhost`                                             |
| SubjectAltName    | `DNS:localhost`, `IP:127.0.0.1`, `IP:::1`                  |
| Extended key use  | `serverAuth`                                               |
| Key usage         | `digitalSignature`                                         |
| Basic constraints | `critical, CA:FALSE`                                       |
| Validity          | One hour before startup to 90 days after startup           |
| Issuer            | The subject itself, because the certificate is self-signed |

The backdated start tolerates small clock differences between machines. The
`CA:FALSE` constraint is what browsers require for a leaf certificate.

## Custom names

`init_https_ephemeral` always uses the defaults above. When a project uses a
different local hostname, build the context with `CertificateNames`:

```zig
const names = uz.tls.CertificateNames{
    .common_name = "api.example.test",
    .dns_names = &.{ "api.example.test", "localhost" },
    .ip_addresses = &.{ "127.0.0.1", "::1" },
};
var credentials = try uz.tls.TlsContext.init_ephemeral(names);
defer credentials.deinit();
```

`CertificateNames` defaults to `common_name = "localhost"`,
`dns_names = &.{"localhost"}`, and `ip_addresses = &.{"127.0.0.1", "::1"}`.
The HTTP/3 variant is `TlsContext.init_http3_ephemeral(names)`.

## HTTP/3 with generated credentials

`App.init_http3_ephemeral` creates both contexts: TCP advertises `h2` and
`http/1.1`, and QUIC advertises `h3`. Bind the QUIC listener separately:

```zig
var server = try uz.App(128).init_http3_ephemeral(init.io);
defer server.deinit();

_ = try server.get("/", index);
try server.listen_udp("0.0.0.0", 8443);
try server.catch_shutdown_signals();
try server.run();
```

## Lifecycle and allocation

Generation runs once inside the initializer, before the event loop starts.
BoringSSL allocates while the key and certificate are built, and the context
keeps its own references. After the call returns, connection setup, handshakes,
record processing, and the request path allocate nothing. Nothing is written to
disk, and the credential is not exportable.

A fresh certificate is created on every start. Restarting therefore invalidates
cached handshakes, which is acceptable for development and wrong for a
production fleet.

## C ABI

```c
uwz_app *app = NULL;
if (uwz_app_create_tls_ephemeral(&app) != UWZ_OK) {
    /* generation failed */
}
/* register routes, listen, run, destroy as usual */
```

`uwz_app_create_http3_ephemeral` mirrors the Zig HTTP/3 variant. When generation
fails, the C layer reports `UWZ_ERROR_INTERNAL`; the Zig layer returns the
specific `Ephemeral*` error.

## Why not production

| Property                       | Consequence                                     |
| ------------------------------ | ----------------------------------------------- |
| Self-signed and not exportable | No external client or trust store can verify it |
| New certificate on every start | Cached sessions do not survive a restart        |
| One certificate per process    | Pinning is not reliable across a fleet          |
| No issuer chain                | Clients need `-k` or a manual exception         |

Generate a trusted local certificate with `mkcert` or your internal CA. Pass the
files to `init_https` for HTTPS, or to `init_http3` for HTTP/3, when a service
worker, mobile device, or strict HTTP/3 client must verify the name.
