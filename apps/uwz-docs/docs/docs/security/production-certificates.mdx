Production deployments pass certificate files to `init_https` or `init_http3`.
The certificate is a PEM chain, the key is a PEM private key, and BoringSSL
validates the pair while the context is created. A bad file fails startup, not
the first handshake.

## Load PEM files

```zig src/main.zig
const std = @import("std");
const uz = @import("uWebZockets");

fn index(_: *uz.Request, response: *uz.Response) void {
    response.text("hello from TLS") catch |err| {
        std.log.err("response failed: {}", .{err});
    };
}

pub fn main(init: std.process.Init) !void {
    var server = try uz.App(128).init_https(
        init.io,
        "certs/fullchain.pem",
        "certs/privkey.pem",
    );
    defer server.deinit();

    _ = try server.get("/", index);
    try server.catch_shutdown_signals();
    try server.listen("0.0.0.0", 3443);
    try server.run();
}
```

`init_http3` loads the same certificate and key into two contexts: one for TCP
(`h2`, then `http/1.1`) and one for QUIC (`h3`).

## Credential requirements

| Item           | Requirement                                                   |
| -------------- | ------------------------------------------------------------- |
| Certificate    | PEM chain with the leaf certificate first                     |
| Private key    | PEM private key that matches the leaf                         |
| Path type      | NUL-terminated Zig slice (`[:0]const u8`)                     |
| Key validation | `SSL_CTX_check_private_key` runs while the context is created |
| Key mismatch   | Rejected at load, not during the first handshake              |

String literals already have the NUL-terminated type. A runtime path must be a
sentinel-terminated buffer; do not pass a plain `[]const u8`.

## Startup failure names

| Error                         | Cause                                                         |
| ----------------------------- | ------------------------------------------------------------- |
| `CertificateLoadFailed`       | The PEM chain could not be read or parsed                     |
| `PrivateKeyLoadFailed`        | The PEM key could not be read or parsed, including a mismatch |
| `KeyMismatch`                 | Defensive context check; the load path already rejects it     |
| `TlsContextCreationFailed`    | BoringSSL could not allocate the context                      |
| `ProtocolConfigurationFailed` | The TLS 1.3 bounds could not be applied                       |

A failed load releases the context that call created. Fix the file and restart;
there is no partial credential state to clean up.

## Startup checklist

1. Keep the `App` value at a stable address after `listen`. The listener stores
   a pointer to it.
2. Call the initializer before `listen`; TLS setup is startup work.
3. Use a chain file, not only the leaf certificate, so clients receive the
   intermediate certificates.
4. Confirm the key belongs to the leaf before deploying. The load check rejects
   a mismatch, but it cannot detect a wrong-but-valid certificate.
5. Call `defer server.deinit()` so the context is released on every exit path.
6. Plan rotation as a rolling restart. There is no hot reload.

## No hot reload

The files are read once while the context is created. Replacing them on disk
does not affect a running process. Rotate by starting a new process and draining
the old one; see [Certificate rotation](/docs/security/certificate-rotation).

## Verify

With a trusted certificate, a normal client verification should succeed:

```sh
curl -v https://127.0.0.1:3443/
```

Read the ALPN line and the certificate subject. A build of `curl` with HTTP/2
support negotiates `h2`; a build without it negotiates `http/1.1`. For a local
self-signed certificate, add `-k` as described on
[Ephemeral certificates](/docs/security/ephemeral-certificates).
