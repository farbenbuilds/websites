Every TCP connection carries an optional HTTP/2 server session. Requests decoded
from HTTP/2 run through the same router, middleware, handlers, and response
helpers as HTTP/1.1, so a route written for one transport works on the other. The
difference is the wire: streams, HPACK header blocks, and flow-control windows.

The session is deliberately bounded. It handles request/response routing well and
does not aim for full RFC 9113 feature parity. The
[HTTPS server example](/examples/https-server) shows the ALPN path on one
application.

## Startup paths

| Path      | Mechanism                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------ |
| TLS       | ALPN selects `h2` ahead of `http/1.1` on `init_https` and `init_https_ephemeral`                 |
| Plaintext | Prior knowledge: a client that opens with the HTTP/2 preface is detected before HTTP/1.1 parsing |
| Upgrade   | Not supported; h2c Upgrade is absent                                                             |

Cleartext prior knowledge means the client sends
`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` as the first bytes. A normal HTTP/1.1 request
on the same listener is parsed as HTTP/1.1.

## What the session implements

- Strict preface, frame-size, and frame-sequencing validation.
- SETTINGS negotiation, PING, GOAWAY, and RST_STREAM.
- Stream identifiers, including the closed-stream rules from RFC 9113.
- HEADERS with CONTINUATION, DATA, trailers, and padding.
- HPACK with a bounded dynamic table.
- Connection-level and stream-level flow control.
- Async response tokens and drain-driven producers.
- RFC 8441 extended CONNECT for WebSocket.

## Boundaries

| Feature                            | Status                                  |
| ---------------------------------- | --------------------------------------- |
| Concurrent streams                 | 8 per connection                        |
| Server push                        | Not supported                           |
| h2c Upgrade                        | Not supported; prior knowledge only     |
| More than 8 streams                | Requires connection-type specialization |
| WebSocket tunnels                  | 1 per connection, no compression        |
| HTTP/2 over cleartext with Upgrade | Not implemented                         |

:::warning[Routing, not full parity]
"HTTP/2 works" on this site means requests route, stream, and respond through the
shared application boundary. It does not mean every RFC 9113 extension,
prioritization scheme, or push mechanism is implemented.
:::
